# Decisions

## Local JSON storage, not a database

Codex initially suggested SQLite because it is a familiar default for project state. I chose one JSON record per project instead. The assessment explicitly keeps this local and single-process, and project records are small, naturally isolated, and easy for a reviewer to inspect. Codex correctly pushed back that raw JSON writes could corrupt state or race, so the implementation uses atomic temporary-file renames and a per-project queue. The cost is that this does not support multiple app replicas or transactional cross-project operations.

## Separate completed status from active step state

Codex proposed tracking only the current stage. I rejected that because a page reopened during Portraits needs to say both that Characters succeeded and that Portraits is in flight. `status` therefore records the last completed milestone, while `stepState`, `activeStep`, and `stepStartedAt` record the active or failed request. This costs a few fields and invariants, but makes resume, failure, and project-list progress unambiguous.

## Start remote work only after persisting RUNNING

The first generated backend sketch returned a Gemini response directly from the button request. I changed that approach. The API persists `RUNNING` before launching work, returns `202`, and the browser polls the stored project state. A second click or browser tab sees the stored state and receives no second Gemini call. The trade-off is polling rather than a WebSocket, but polling is enough for this small local app and still lets each image appear independently.

## Manual retry only

Codex proposed exponential retry around image calls, which would improve transient failures but can quietly multiply image cost. I overrode it because the brief expressly requires user-triggered retries only. Errors mark the current stage `FAILED`, preserve prior output, and leave a single retry action. The cost is a user must return and click retry after a temporary service failure.

## Gemini interaction chaining and hard caps

The notebook makes the book a File API upload and chains interaction IDs for text prompts. I kept that mechanism rather than sending the book contents on every request. Portraits are saved locally and attached as reference images to the final scene call. The app slices structured output on the server to two adult characters and one chapter even if a model returns more. That avoids a client-side bypass and bounds image cost, at the expense of intentionally limited story coverage.

## Small purpose-built UI over a component library

Codex suggested adding a component library for dialogs and cards. I kept native, semantic controls and a small CSS token layer because the interaction surface is compact and no complex modal or menu primitive is necessary. The supplied Gradion warm-orange system remains recognizable, while loading, empty, failure, keyboard focus, mobile collapse, and reduced-motion states are explicit. The cost is fewer prebuilt primitives if the app grows.

## Codex's Gemini Interactions API shape was invented, not verified

Codex's first draft of `server/gemini.ts` compiled and passed the pipeline tests, but before spending any quota on it I had Claude Code check it against the actual `@google/genai` SDK sitting in `node_modules`, model choice included. It didn't match. The code read `interaction.output_text` / `interaction.output_image` — fields that don't exist anywhere in the SDK's own type definitions. The real response is `outputs: Array<ContentBlock>`, a content-block array you scan by `type`, the same shape OpenAI's Responses API and Anthropic's Messages API use. It also crammed a JSON-schema wrapper and image aspect ratio into an invented `response_format` object instead of the real, separate `response_modalities`, `response_mime_type`, and `generation_config.image_config` fields, and used `mimeType` where the SDK wants `mime_type` on inline image parts. All of it compiled cleanly only because every call was cast with `as never` to defeat the type checker — a smell I should have caught on first read, not after asking for an audit. As written, every real Gemini call would have failed immediately on the first request; `data/` had never even been created on disk, so nobody had run it once. I had `server/gemini.ts` rewritten against the verified shapes and added `server/gemini.test.ts`, which mocks the SDK client directly instead of the whole `GeminiGateway` interface, so this exact bug fails a test the next time instead of shipping silently. Cost: one more test file to keep in sync with the SDK, and I still owe the real-key UAT run in the README before submitting — passing shape tests proves the request/response mapping is right, not that the prompts produce good illustrations.

While checking that, I almost "fixed" the model IDs too — `gemini-3.7-flash` and `gemini-3.1-flash-lite-image` looked like a plausible hallucination (version 3.7 with no 3.2–3.6 in between). I checked Google's docs and a web search before touching them: both are real, current, GA model names (`gemini-3.1-flash-lite-image` is Nano Banana 2 Lite). Left as-is. Worth recording because it's the same instinct that caught the real bug above — "looks hallucinated" isn't proof by itself, so both times I checked instead of trusting the pattern-match.

**Update, after actually running it with a real key:** the type-level audit above was real but incomplete — checking a library's shipped types is not the same as calling the live endpoint, and this assessment's own §09 says so directly ("harness... something broke"). The first real call to Style returned `400 The legacy Interactions API schema is no longer supported. Please upgrade... to version >= 2.0.0`. The installed SDK was `^1.30.0` → resolved `1.52.0` — a version that satisfies the package.json range and has internally consistent types, but targets a schema the live API had already retired. Upgrading to `@google/genai@2.17.1` and re-reading its types turned up a genuine surprise: v2's `Interaction` response restores `output_text` / `output_image` as SDK-computed convenience fields (`response_modalities`/`response_mime_type` are now `@deprecated`, and `response_format` is a typed per-modality object again) — which is much closer to **Codex's original, pre-audit code** than my "verified" v1 rewrite was. So Codex's real bugs were narrower than I first reported: one wrong field name (`mimeType` instead of `mime_type`, in two places) — not the whole response-shape model. I got there by testing the fix against a real call, not by re-reading types harder; a second, more careful type audit of v1 would have "confirmed" the wrong answer just as confidently as the first one did. The next real call surfaced a second, unrelated real bug: `image/png` isn't accepted for `response_format.mime_type`, only `image/jpeg` — one-line fix, only findable by calling the endpoint.

## Image model: still blocked on this key's billing, tried two Nano Banana variants

The .env.example default was Nano Banana 2 Lite (`gemini-3.1-flash-lite-image`). A real Portraits call against it returned `429 ... limit: 0 ... model: gemini-3.1-flash-lite-image` — a search confirmed Nano Banana 2 / 2 Lite has no free-tier quota via the API at all, API-key billing or not. I switched the default to `gemini-2.5-flash-image`, the original Nano Banana, expecting an actual free allowance. A real call against *that* also came back `429 ... limit: 0 ...` (aliased server-side to `gemini-2.5-flash-preview-image` in the error text). Two different image models, same `limit: 0`, on the same key — that's an account-level entitlement gap, not a per-model quirk, and not something a third model name would fix. The text model (`gemini-3.7-flash`) does have real free quota — a later real 429 on it read `limit: 20`, a plain rate limit from repeated UAT runs in a short window, not a zero entitlement. I'm leaving the default at `gemini-2.5-flash-image` (still the right call once billing is on) and recording this as an open item rather than guessing at a third model name against the same unbilled project.

## Test suite deleted real project data because it shared the live data directory

`Storage` resolved its root to `<cwd>/data` unconditionally, and `pipeline.test.ts`'s `afterEach` did `rm("data", { recursive: true, force: true })`. That's the same folder a locally running `npm start` writes real projects to. Running `npm test` in that state — which is exactly what a reviewer does per the README — deleted a real, hand-verified UAT project mid-session, including two genuine failed Portraits attempts that took real quota to produce. Not an AI-authored bug I caught by review; I hit it by using the app and the test suite the way a developer actually would, at the same time. Fixed by making `Storage`'s root a constructor argument — tests now pass an isolated `os.tmpdir()` directory instead of touching the shared one. Cost: one more constructor parameter, and every existing on-disk project needed a migration path for the new `history` field, since the default root didn't change for real usage.

## If I had one more day

The SDK-shape test (`server/gemini.test.ts`) covers the request/response mapping, and real-key runs through Style and Characters (multiple, including a retry after a genuine transient failure) confirm the mapping holds in practice, not just in a mocked test — see `data/` on the reviewer's own run, or the attempt history panel in any project that hit a real error. Attempt history per stage shipped instead of staying a someday. What's left: Portraits/Chapters/Illustrations still want one real successful run once billing is enabled on the Gemini key used for grading, and a batch mode to generate more than one project's worth of illustrations without a human clicking each step would be the next thing after that.
